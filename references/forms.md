# Form persistence checks

Use this reference when an upgrade touches Rails form helpers, parameters,
validation, callbacks, nested attributes, or the JavaScript that submits them.
These are conditional regression recipes, not permission to change business rules.

## Trace the stored result

For each affected form, record the route/verb, role/tenant, HTML or JS response,
input names, parameter reader, model callbacks, nested associations and destination.
Render the real template. Inspect successful browser controls (including hidden
inputs), then submit that payload through the real request path. A handcrafted
hash with the correct keys cannot detect incorrect names generated by the view.
Reload the parent and children from storage, then reopen the edit/show page.

Keep request/model checks in the app's existing framework. Use a browser check
where JavaScript builds the payload, changes forms, uploads files or handles errors.
Do not replace these checks with a universal script that writes to an unknown DB.

## Regression matrix

| Contract | Cases | Assert |
| --- | --- | --- |
| Checkbox collections | Select, save, reopen, deselect one, clear all, submit unchanged | Exact persisted child IDs, no duplicates or phantom rows, correct checked state |
| Omitted and empty fields | Absent key, explicit empty list/string, false/zero, partial update | Preserve absent fields where intended; clear only when the form/API contract requests it |
| Nested records | Create, edit, `_destroy`, blank rejected row, invalid sibling | Correct identities, transaction behavior, visible errors and no unauthorized child changes |
| Derived values | Create, repeated update, nested deletion, failed validation | Stored timestamps/status/totals after reload; no accidental overwrite or duplicate jobs |
| Dates and times | Blank/placeholder, same-day, overnight, configured zone, DST boundary | Intended local date/time and persisted UTC instant; invalid input handled visibly |
| Upload modal/sidebar | Open, upload, duplicate name, invalid file, edit/delete, reopen | Correct route and parent, storage metadata, visible success/error, permission-specific replacement behavior |
| User/tenant scope | Allowed role, read-only role, another tenant's parent/child IDs | Denial and zero writes, queued jobs or uploaded objects outside the authorized scope |
| Invalid save | Invalid create and update in each used response format | Submitted values and nested rows retained, field/base errors visible, no false success |

## Mechanisms to inspect

- A form builder's bracketed method name may produce a different `name` than
  expected. Compare rendered names with permitted roots and nesting. Use supported
  builders or an explicit name only where necessary; retain IDs used by scripts.
- Hidden checkbox fallbacks and indexed hashes affect the decoded payload. A
  collection index is not necessarily the selected record's ID. Preserve the
  application's explicit clear-all signal; absence can mean an omitted partial
  update. Do not convert every missing field to an empty collection.
- Nested deletion uses an associated record ID and the configured destruction
  policy. Records marked for destruction can still be in the in-memory collection
  before save; derived totals/status must follow the intended surviving-record
  contract. Verify both persistence and failed-save behavior.
- Assigning an attribute in `after_save` need not persist that assignment. Prove
  the value after reload before moving it to an appropriate validation/save hook.
  Preserve create-only and user-entered values; avoid recursive save callbacks.
- Do not weaken a presence validation or add blanket `optional: true` to make a
  form pass. Reconstruct valid/invalid transitions and distinguish a framework
  regression from an older business-rule defect.
- Parse date/time values in the configured zone, not a current timezone
  abbreviation or a guessed hour offset. Overnight rollover is an application
  rule; test it rather than introducing it automatically.
- Scope attachment lookup and submitted foreign IDs through the authorized
  parent. Derive ownership/type server-side; preserve explicitly supported legacy
  references without accepting arbitrary polymorphic types from a form.
- Inspect actual modal links and form action/method after JavaScript replacement.
  A valid upload endpoint does not help if the sidebar opens an unrelated form.

## Spec shape

Arrange an existing record with identifiable child rows, including an excluded
tenant/role case. Render the edit page and assert its input contract. Submit one
real user transition. Assert the response, reload the rows, compare exact values
and child IDs, then render again. For a clearing/deletion regression, assert what
was preserved as well as what was removed. For derived fields, repeat the save to
check stability. Use the target database adapter and isolated storage/services.

The Rails [form helper guide](https://guides.rubyonrails.org/form_helpers.html#form-input-naming-conventions-and-params-hash)
explains the name-to-parameter contract. The [nested attributes API](https://api.rubyonrails.org/classes/ActiveRecord/NestedAttributes/ClassMethods.html)
documents associated IDs, destruction and rejection. Consult documentation for
the target Rails version; do not copy application-specific parameter repairs.
